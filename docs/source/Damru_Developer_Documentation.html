01Project Overview

What this repository is, and how its pieces fit together.

Damru is a TypeScript monorepository-style project containing a Next.js website, a Next.js route-handler backend, an administration interface, an Expo/React Native mobile application, Mongoose models, and business services. MongoDB is the persistent store.

The website and mobile client are two independent front doors that share the same backend endpoints. The backend owns authentication, commerce validation, reward eligibility, progress tracking, and redemption — none of that logic is duplicated or re-implemented on either client.

Reading this document Each section describes confirmed repository structure and behavior as implemented today. Where a detail could not be confirmed from the codebase or committed configuration, it is called out explicitly rather than assumed.

05Authentication Architecture

Two separate identity systems: customer sessions and admin auth.

Customer endpoints cover registration, OTP sending and verification, login, logout, current-user lookup/update, and password reset. Customer route handlers obtain the authenticated user through the established customer-session helper and return 401 when absent. Admin authentication uses the project's NextAuth configuration and permission helpers.

Password and verification flows must remain server-owned Secrets must never be returned to clients. OTP values are handled entirely server-side as part of the verification flow.

08Validation and Error Handling

The layered checks every request passes through.

  1. Route handlers validate request shapes, numeric ranges, enum membership, dates, and object identity.
  2. Authentication helpers establish customer/admin identity.
  3. Permission helpers authorise administrative capabilities.
  4. Business services recompute eligibility and do not trust frontend progress.
  5. Mongoose schemas enforce required values, enums, bounds, and unique indexes.
  6. Conditional atomic updates and unique idempotency keys protect financial operations.

Route handlers generally return JSON errors with appropriate 400, 401, 403, 404, or 500 status codes. Website and mobile callers show safe messages. TanStack Query retries transient failures once but avoids retrying 4xx failures.

09Damru Reward Architecture

The single controlled path every Damru credit or debit travels.

Business Event
↓
Backend Eligibility / Configuration
↓
awardDamru()
↓
Unique Idempotency Key
↓
DamruTransaction Credit
↓
Atomic User Wallet Increment

lib/rewardEngine.ts is the central issuer. awardDamru() creates the ledger record, atomically increments damruBalance and damruTotalEarned, patches balanceAfter, optionally creates a private coupon, and attempts a notification email. Duplicate transaction keys return a duplicate result without another balance change.

redeemDamru() validates the order and redemption policy, conditionally decrements the wallet, and writes an order-bound debit. adjustDamru() records the acting administrator and required reason.

Never introduce a direct wallet write Direct wallet writes must not be introduced outside these controlled primitives — every new reward-producing feature must call awardDamru(), redeemDamru(), or adjustDamru().

11Daily Streaks

Server-authoritative streak calculation and reward issuance.

lib/dailyStreak.ts contains pure date/projection logic. lib/getDailyStreakConfig.ts loads normalised configuration. checkAndAwardDailyLogin() uses a server date string, a conditional user update, and a daily-login:{userId}:{date} transaction key. Cycle behavior and grace-period decisions remain fully admin-configurable rather than hardcoded.

lib/dailyStreak.ts

Pure streak projection and reward-day resolution logic.

lib/getDailyStreakConfig.ts

Loads and normalises the admin-configured day-reward schedule.

Idempotency key

daily-login:{userId}:{date} — one credit per eligible calendar day.

12Achievements

Long-term progress milestones evaluated by a shared engine.

lib/achievementEngine.ts resolves progress for ORDER_COUNT, LIFETIME_SPEND, LOGIN_STREAK, PROFILE_COMPLETE, and ACCOUNT_AGE_DAYS conditions. Definitions are stored in Achievement; per-user state is stored in UserAchievement. Unlock rewards use the central reward engine and a deterministic idempotency identity, so re-evaluating an already-unlocked achievement never double-pays.

13Missions

Time-bound challenges with event-level deduplication.

lib/missionPeriod.ts calculates period boundaries. lib/missionEngine.ts updates applicable missions for ORDER_COUNT, SPENDING_AMOUNT, LOGIN_STREAK, and PROFILE_COMPLETE conditions. MissionEvent prevents a repeated source event from incrementing progress twice — this is a separate dedup layer from mission-completion idempotency itself.

Supported periods: ONE_TIME DAILY WEEKLY MONTHLY CAMPAIGN

14Referrals

Code generation, qualification, and dual-sided reward issuance.

lib/referralEngine.ts, lib/referralCode.ts, ReferralConfig, and Referral together implement code generation, registration association, first eligible/delivered-order qualification, referral limits, verification checks, reward delay policy, and duplicate-safe reward issuance for both sides of a referral. Referral API output masks or omits sensitive referred-user information.

15Loyalty Tiers

Configurable tier ladder with trusted, backend-computed qualification.

LoyaltyTier stores name, code, rank, qualification type, min/max range, multiplier, benefits, badge, an optional upgrade bonus, and an activation flag. Active tiers must share a single qualification type; invalid and overlapping ranges are rejected at the model/admin layer. Only the highest tier may omit a maximum.

lib/loyaltyEngine.ts loads the active ladder, calculates trusted qualification from delivered orders or lifetime Damru totals, resolves the current and next tier, returns progress and benefits, persists tier identity on the user, and optionally issues an upgrade bonus through awardDamru() with the idempotency key loyalty-tier:{userId}:{tierId}.

Multipliers are centralised in getLoyaltyRewardMultiplier() and currently apply only when the caller explicitly identifies ORDER_REWARD. applyLoyaltyMultiplier() uses integer rounding. Birthday, anniversary, login, achievement, mission, referral, admin-adjustment, and redemption transactions are not multiplied by default.

Reconciliation script scripts/recalculate-loyalty-tiers.ts is rerunnable, reports only aggregate counts, and deliberately sets issueBonus: false so re-running it never re-pays upgrade bonuses.
Known debugging note A standalone loyalty helper runner was observed to block/hang during Mongoose module initialisation in this execution environment during documentation research; no database write occurred. Investigate module-level side effects if a future script exhibits the same symptom.

16Checkout and Order Lifecycle

From cart to delivery, and the trusted transition that triggers rewards.

Cart
→
Address
→
Coupon / Damru
→
Payment Selection
→
Order

Backend routes validate ownership and recompute sensitive totals server-side. Order states are pending, confirmed, preparing, out_for_delivery, delivered, and cancelled; payment states are pending, paid, and failed.

The delivered transition is the trusted reward trigger The delivered transition in app/actions/orders.ts invokes the reward engines (first-order, achievements, missions, referral qualification, loyalty evaluation). Individual engines remain idempotent so a replayed transition never duplicates a financial reward.

17Website Architecture

App Router structure and where rewards UI lives.

The App Router website is under app/(website). Customer rewards are integrated into my-profile/page.tsx and supported by lib/rewards types, API wrappers, provider state, and analytics event names. CSS lives under styles/website. Client components handle browser interaction while route handlers and server actions retain protected, server-only logic.

18Mobile Architecture

Expo Router structure and the shared-API pattern.

The Expo app uses mobile-app/src/app for routes. services/rewardsApi.ts wraps the shared reward endpoints; types/rewards.ts defines response contracts; queryClient.ts owns retry/cache defaults. Rewards include dashboard/profile integration plus dedicated history, achievement, mission, referral, and loyalty screens, each with loading, retry, error, and pull-to-refresh handling.

19Admin Architecture and Permissions

One dashboard, module-level permission gating.

Admin routes and pages are grouped under app/admin. The rewards page contains tabs for reward rules, Damru config, daily rewards, achievements, missions, referrals, loyalty tiers, and individual customer rewards. getAdminPerms() supports server actions and checkApiPerm() protects route handlers. Manager role/permission editing reuses the same permission model.

Known permission gap role === "admin" bypasses all permission checks in the current implementation — only the moderator role is actually restricted by granular permissions. checkApiPerm also has no null-check on the admin lookup, and an inactive admin (isActive: false) is never enforced at the permission layer. These are documented findings, not yet remediated.

20Email and Scheduled Work

Transactional messages and the rewards scheduler.

lib/email.ts centralises transactional email behaviour over Nodemailer/SMTP. The rewards scheduler endpoint is /api/internal/rewards/run-scheduler; its deployment schedule is configured in vercel.json. Scheduler access must remain secret-protected. The code supports verification/reset and reward-related message flows without placing provider secrets in client code.

21Security Properties

What's already enforced, confirmed directly from the code.

Hashed passwords

Protected verification/token material, never stored or returned in readable form.

Authenticated APIs

Customer endpoints require a valid session and enforce ownership checks.

Permission-gated admin

Administrative routes are checked against assigned module permissions.

Reward idempotency

Unique keys guarantee a reward can never be issued twice for the same event.

Atomic wallet updates

Balance changes use conditional atomic operations with full ledger history.

Order-bound redemption

Damru redemption is tied to a specific, owned order and re-validated server-side.

Private coupon isolation

Customer-specific coupons are never visible to another customer.

Backend-authoritative progress

Reward and loyalty progress is always computed server-side, never trusted from a client.

Safe reconciliation output

Reconciliation scripts report aggregate counts only, no personal data.

Known gaps (documented, not remediated in this pass) No rate limiting exists anywhere in the current implementation. OTP values are carried inside a signed-but-not-encrypted JWT rather than being encrypted at rest. Coupon perUserLimit/usedBy fields exist on the schema but are not enforced or updated by any route, and coupon usageLimit has a TOCTOU race under concurrent redemption. See also the admin permission gap noted in Section 19.

26Common Extension Workflows

Repeatable patterns for extending the platform safely.

Add an API

Create a route handler under app/api, authenticate first, validate input, call an existing service/model pattern, return safe JSON, and add web/mobile types where consumed.

Add a reward safely

  1. Define the trusted backend trigger.
  2. Load server-side configuration and validate eligibility.
  3. Generate a deterministic idempotency key.
  4. Call awardDamru(); never increment balance directly.
  5. Attach useful non-sensitive transaction metadata.
  6. Add administration configuration only if required.
  7. Extend API and client display types.
  8. Test the same event twice.

Add an achievement or mission

Extend the model enum and engine calculation, integrate only at an existing trusted event, add admin/customer labels, and verify progress plus duplicate-event behaviour.

Add a mobile rewards screen

Add an Expo Router file, a typed service function, loading/error/retry/refresh states, query invalidation where mutations occur, and a navigation entry from the rewards profile section.
